# bcrypt хеширане на клиентски пароли + затваряне на 4 свързани изтичания

ALTER/UPDATE-скриптове, които вкарват `klienti.parola_hash` (bcrypt) редом с
досегашния plaintext `klienti.parola`, сигурен reset-token механизъм за
`zabpas`, и изчистват plaintext паролите, които изтичат независимо от
хеширането — в `greshni_logove` (лог на неуспешни логини) и `tek`
(механизъм за пре-попълване на формата след грешка).

Пълният дизайн: `docs/superpowers/plans/2026-09-01-password-hashing.md`
(тази поддиректория е само SQL-ът; договорът с PHP кода — feature флагове,
`parola.php` helper, `citte/vlizali.php` и т.н. — е описан там).

| | От (baseline) | До (край) |
|---|---|---|
| `klienti.parola` | `varchar(127) utf8mb3_unicode_ci`, `urlencode(plaintext)` | смесена (plaintext или bcrypt) по време на rollout, после `varchar(255) ascii_bin`, само bcrypt `$2y$`/`$2b$` (07) |
| `klienti.parola_hash` | не съществува | `varchar(255) ascii_bin`, staging колона — пълни се само от CLI backfill скрипта (01), merge-ва се в `parola` и се трие (07) |
| `zabpas.koda`/`akt` | `md5(time())` — познаваем токен | непроменени, после изтрити (06) |
| `zabpas.token_hash` | не съществува | `char(64) ascii_bin`, sha256 на случаен 256-битов токен |
| `greshni_logove.pass` | plaintext на въведената парола | `''` (03), после изтрита (05) |
| `tek` (prm sspp/nnpp1/nnpp2) | plaintext пароли | изтрити редове (04) |

## Философия: fail-fast, не идемпотентност

- **Гол SQL. Нула guards.** Няма `IF NOT EXISTS`, няма `information_schema`
  проверки в самите миграции, няма `INSERT IGNORE`.
- **Не е идемпотентно — нарочно**, с две изключения: `03`-ото `UPDATE` и
  `04`-ото `DELETE` съвпадат с 0 реда на втори run и просто нищо не правят.
  Всичко останало гърми на втори run — това е **сигналът**, а не шум.
- **Без `USE`.** Избираш базата при пускане: `mysql -D <db> < файл.sql`.
- **Прекъсването е половинчато.** Гол SQL спира на statement-а, който е
  гръмнал, и оставя предходните приложени. `00-preflight.sql` и
  `08-verify.sql` съществуват точно затова.

## Ред на пускане

```
imartap:     00 → 01 →           [backfill] → 07 стъпка 1 → [деплой] → 03 →           05 →      07 стъпки 2-3 → 08
Регионална:  00 → 01 → 02 →      [backfill] → 07 стъпка 1 → [деплой] → 03 → 04 →      05 → 06 → 07 стъпки 2-3 → 08
```

За разлика от оригиналния дизайн, тук има **само един** код деплой — кодът
пише bcrypt директно в `parola` от началото. И [vlizali.php](../../../public_html/citte/vlizali.php)
(вход), и [smenparoh.php](../../../public_html/citte/smenparoh.php) (смяна
на парола) вече нямат legacy fallback изобщо — приемат само bcrypt-оформена
`parola`, без изключение. Няма повече feature-flag „kill switch" — flag 5182
беше точно за тази цел и вече не се чете никъде в кода, затова е изцяло
премахнат от този дизайн (само 5183, отделен и все още активен, остава).
Това обръща реда: **backfill (+ 07 стъпка 1) трябва да приключат ПРЕДИ
деплоя, не след него** — деплой на код без legacy fallback, докато има
немигрирани редове, означава мигновено заключване на всеки такъв клиент
извън паролния вход (reset-по-имейл пътят остава работещ, той не пипа
`parola`).

**Редове с null байт в паролата — задължителен reset ПРЕДИ деплоя.**
Backfill-ът съзнателно прескача такива редове (bcrypt/`urldecode` не могат
да ги обработят коректно) — за тях `parola` остава plaintext завинаги,
докато клиентът не си смени паролата. След деплоя такъв клиент не може да
влезе с текущата си парола по никакъв начин — единственият изход е reset
линк, изпратен проактивно.

Задължителни зависимости:

- **00 преди всичко** — доказва, че `parola_hash`/`token_hash` наистина
  липсват (иначе 01/02 просто ще гръмнат — това е добре, но по-добре знай
  причината предварително) и че feature-flag id 5183 е свободен.
- **01 (и 02 на регионалните) преди backfill-а** — backfill скриптът пише в
  колона, която трябва вече да съществува на ВСЯКА база. `08-verify.sql`
  check A/C е гейтът тук.
- **Backfill преди 07 стъпка 1** — merge стъпката копира `parola_hash` в
  `parola`, значи има смисъл само след като backfill-ът е попълнил
  `parola_hash` за старите редове.
- **07 стъпка 1 преди деплоя** — виж обяснението по-горе: деплойнат ли се
  8-те PHP файла преди `parola` да е bcrypt навсякъде (или клиентът да има
  reset линк), този клиент не може да влезе. `08-verify.sql` check D = 0 (или
  съзнателно приет остатък само от `\0`-редове с изпратени reset линкове) е
  гейтът тук, не просто препоръка.
- **07 стъпка 1 преди 03/04** — `03`/`04` пускат само след деплоя (виж
  предупреждението във всеки файл).
- **03 преди 05, с недели между тях** — 03 изпразва `pass`, 05 маха
  колоната. Същото за 04→06 (седмици, не недели — `koda`/`akt` живеят само 1
  час) и особено за 07 стъпки 2-3 (re-collate, после трие `parola_hash` —
  минимум 2–4 седмици след деплоя, вижте предупреждението в самия файл).
- **07 стъпки 2-3 само след `08-verify.sql` check D = 0 навсякъде** и офлайн
  `mysqldump` на `klienti`, пазен извън сървъра. Стъпка 2 (re-collate към
  ascii) е разрушителна ако се пусне рано — конвертира `parola` към ASCII
  charset, което поврежда/гърми на всеки ред, който все още е реален
  plaintext (кирилица). Стъпка 3 е необратима.

## Пускане

**По един файл, ръчно, четеш изхода на всеки.**

```bash
DB=inmarta                # или imartap, или друга регионална
CT=lamp-mysql8

# Pre-flight — всеки ред трябва да е OK, ALREADY DONE, или очакван ERROR 1146.
docker exec -i "$CT" mysql -u root -p<pass> -D "$DB" --table --force < 00-preflight.sql

# Миграциите — по една, с проверка на exit code
docker exec -i "$CT" mysql -u root -p<pass> -D "$DB" < 01-add-klienti-parola_hash.sql; echo "exit=$?"
docker exec -i "$CT" mysql -u root -p<pass> -D "$DB" < 02-zabpas-secure-token.sql;      echo "exit=$?"
# … и така нататък по реда в run-матрицата, с деплоите/backfill-а между тях

# Верификация — след всеки файл, не само накрая
docker exec -i "$CT" mysql -u root -p<pass> -D "$DB" --table --force < 08-verify.sql
```

`--force` е **само** за `00` и `08` (read-only; продължават покрай очаквани
`ERROR 1146` за таблица, която не съществува на този target — виж таблицата
"Кои таблици на коя база"). **Никога** на `01`–`07` — там спрелият run е
целият смисъл.

Гол SQL спира на statement-а, който е гръмнал, и оставя предходните
приложени.

1. Прочети грешката — казва точно кой обект е проблемният.
2. Пусни `08-verify.sql`, за да видиш какво реално е кацнало.
3. Довърши липсващото ръчно, или довърши файла от следващия statement.

Най-честите:

| `08` check F/G показват реални стойности след 03/04 | Кодовият деплой B все още не е спрял записа — провери деплоя преди да подозираш миграцията |

## Rollback

Схемните добавяния (`01`, `02`) са тривиално обратими — колоните са
nullable и нищо старо ги чете:

```sql
-- всяка база
ALTER TABLE klienti DROP COLUMN parola_hash_data, DROP COLUMN parola_hash;
-- само регионалните
ALTER TABLE zabpas DROP INDEX token_hash, DROP COLUMN izpolzvan, DROP COLUMN izticha, DROP COLUMN token_hash;
```

`03`/`04` (purge) **нямат rollback** — изтритите/изпразнените plaintext
пароли не се възстановяват от нищо друго освен резервно копие. Това е
нарочно: целта им е точно да не съществуват никъде повече.

`05`/`06`/`07` (drop) **нямат SQL rollback** — само `mysqldump` възстановка.
`07` стъпки 2-3 са единствените стъпки в целия set, за които това
предупреждение е задължително, не просто препоръка (виж коментарния блок в
самия файл). `07` стъпка 1 (merge) е безопасна и идемпотентна — не се брои.

**Кодовият деплой вече НЕ е универсално безопасен за rollback в нито една
посока**, за разлика от оригиналния дизайн. Там `parola` оставаше непроменен
plaintext през цялата фаза B, специално за да може деплоят винаги да се
revert-не безопасно. Тук `vlizali.php` (вход) няма legacy fallback изобщо —
приема само bcrypt. Това означава:
- деплой **преди** backfill + `07` стъпка 1 да приключат → всеки все още
  plaintext ред губи паролен достъп мигновено (виж run-реда по-горе);
- revert на деплоя **след** като е обработил реален трафик (нови
  регистрации, смени на пароли) → старият код очаква `parola` да е plaintext
  и отказва да автентикира редовете, които новият код вече е превърнал в
  bcrypt.

Няма повече flag-базиран kill switch — нито `vlizali.php`, нито
`smenparoh.php` четат `$prevodite[5182]`. Единственият сигурен lever и в
двете посоки е офлайн dump/restore на `klienti` към точния момент преди
деплоя, не код rollback.

## Бележки

- **Булева конвенция:** `izpolzvan` следва проектната конвенция 2=on/да,
  1=off/не (виж `kurieri.has_office` в `deploy/14`) — не 1/0.
- **`ascii`/`ascii_bin`, не `utf8mb3_unicode_ci`** за `parola_hash` и
  `token_hash`: и двете стойности са винаги чист ASCII (bcrypt: `[./A-Za-z0-9$]`,
  sha256 hex: `[0-9a-f]`), а `_bin` пази евентуално `WHERE` сравнение
  byte-exact вместо case-insensitive. `parola` получава същото третиране по-
  късно, в 07 стъпка 2 — едва след като е гарантирано, че всеки ред вече е
  bcrypt (виж предупреждението в самия файл: конвертиране към ASCII, докато
  има реален plaintext, поврежда/гърми на кирилица).
- **`parola_hash` е `varchar(255)`, не `char(60)`** — bcrypt е точно 60
  символа, но 255 оставя място за argon2id по-късно без нова миграция.
  Същият избор важи и за `parola` след 07 стъпка 2.
- **Feature-flag id 5183 НЕ се създава от тази миграция.**
  `promenliviprevodi` се управлява извън SQL migration системата (виж
  `00-preflight.sql` check D) — добави го ръчно по обичайния за проекта
  начин. (Id 5182 беше запазен за legacy fallback kill switch в по-ранна
  версия на този дизайн — вход/смяна на парола вече нямат legacy клон
  изобщо, значи 5182 не участва никъде и е изваден от плана.)
- **`greshni_logove.komentar` вече съществува** (TEXT, неизползвана) — 03 не
  я пипа; кодовият деплой B я запълва с причината за неуспешния логин
  (`'email'`/`'pass'`/`'otorizacia'`) вместо да пише `pass`.
